# SST Agent Review

Use this skill when the user requests a local review or continuation of an existing review. Do not invoke a reviewer proactively after coding or committing. State that this skill is being used at the first invocation. Follow the user's approval, Git, delegation and context-boundary rules; honor actions already explicitly authorized. A request to review does not authorize fixes, publication, additional reviewers or repeat runs.

At the beginning of a new invocation, before review work, run `python3 /path/to/this/skill/scripts/install_skill.py --check` when permitted by the current sandbox and user rules. This checks managed installations at most once per 24 hours; repository and manual copies stay unchanged. Read the SKILL.md at the concrete version path returned as `Skill`, then use its `Helper` path and adjacent files for the rest of this invocation. Do not repeat the update check after rereading, switch versions between helper commands, or move an active author workflow to a new version. Existing reviewer processes retain their original runtime and files. Updates never start reviewers.

If updating is blocked by sandbox permissions or network access, tell the user the check or update could not finish and show the manual update command: `curl -fsSL https://github.com/sintoniastrategy/agent-review/releases/latest/download/install.sh | bash`. Ask them to run it in a normal terminal outside the sandbox. Do not request broader permissions or install prerequisites automatically. The installed version remains usable; continue with its concrete path only when the user's workflow rules permit. If the updater itself cannot be executed, resolve this skill's existing path and report the restriction instead of claiming an update succeeded.

Keep the author session and its task context. Each review runs in a fresh interactive Claude or Codex session with the durable journal. The user should not need to read this skill or edit configuration: explain each meaningful stage, recommend the usual next step, and offer alternatives in conversation. Ask once at a branch when a choice is needed, then end the turn and wait. Do not ask again for an already explicit choice.

Settings are plain INI files: bundled defaults.ini, personal ~/.local/share/sst-agent-review/config.ini, and worktree .agr/config.ini, in increasing precedence. The single bundled file contains shared [review] settings and defaults for both agents in separate sections. [review] holds agent, preset, scope, runtime and window_name. [claude] and [codex] each hold model, effort, auth and credentials_file with their own supported values. Edit only requested keys in the appropriate section, preserving other settings and formatting; remove a key to inherit it again. Agent sections may appear without [review] in override files. Legacy model/effort/auth/credentials_file under [review] belong to the agent selected at that layer, inheriting the preceding layer's agent or Claude. Explicit agent sections win within a file; selecting another agent on the CLI never transfers those preferences. There is no configuration-writing command. Keep custom presets outside versioned releases, using absolute paths for shared personal presets. A legacy config.json without a replacement config.ini requires explicit conversion; never silently discard it.

Claude remains the default, with opus and xhigh effort. Codex defaults to gpt-6.1-sol with xhigh effort and uses pinned CLI 0.160.0. Both support the same presets, publication protocol and follow-up workflow. Settings are frozen per prepared reviewer.

The bundle needs Python 3.9+, Git, tmux and authentication for the selected reviewer: a Claude subscription or Codex ChatGPT login. Docker is the default on Linux and macOS; runtime = auto also selects Docker. Native remains an explicit option without completed release validation. Native setup also needs curl. Existing CLI logins are reused while the bundle installs its own pinned runtime and clean profile; user executables and aliases are not launched. For Claude, auth accepts auto/file/keychain. Auto uses an explicit credentials_file, otherwise the default macOS Keychain entry if present, then $CLAUDE_CONFIG_DIR/.credentials.json or ~/.claude/.credentials.json. For Codex, auth accepts auto/file/keyring. Auto uses an explicit credentials_file, otherwise $CODEX_HOME/auth.json or ~/.codex/auth.json if present, then that home's macOS Keychain entry. Codex auto does not read the user's config.toml; select keyring explicitly when both stores exist and Keychain is intended. Custom Claude Keychain profiles are not discovered. Resolve scripts/review.py relative to this SKILL.md and invoke it with --repo ABSOLUTE_WORKTREE. Read [the command reference](references/commands.md) for exact operations and file locations. The helper never commits, fetches, creates worktrees or publishes to external services.

Preparation and launch:
1. Establish task scope, worktree and explicit base using the supplied context. Git does not store a parent branch. Let the helper calculate HEAD, merge base, commit range and a snapshot including staged, unstaged and non-ignored untracked files. Detached HEAD is valid with an explicit base. Missing Git history or an ambiguous base needs human input; never invent a whole-folder review.
2. Read the INI settings and explain the proposed review in plain language. Defaults are Claude, opus, xhigh, preset default, scope full, runtime docker and auth auto. Use preflight --base REF --human with the same agent/model/effort/preset/scope/runtime overrides intended for prepare. It validates and shows effective settings, configuration paths, required local tools, the selected base, authentication source and Docker connectivity or native sandbox prerequisites without installing or starting a model. Preparation repeats tool and credential checks before runtime setup. Managed Claude checks subscription authentication; managed Codex requires login status to report ChatGPT before inference. Report missing prerequisites and follow recovery approvals. Missing native Claude sandbox dependencies are an expected fallback: explain that commands can run with the user's full permissions. Codex has no unsandboxed retry. Do not install dependencies or change the runtime automatically. Native Keychain access and the host credential bridge may require macOS approval on first use.
3. Start a cycle with init --base REF --task-file FILE, or use sessions and status --human for an existing cycle. There is one cycle per worktree. Use note --text-file FILE for new author context. Read relevant saved decisions, not just counts.
4. Use prepare --human to freeze inputs, then start REVIEWER --human only for the requested run. Preparation uses the configured selection; flags can override agent, model, effort, preset, scope and runtime for that reviewer. Select Codex with agent = codex or prepare --agent codex. State the tmux window, attach command and artifact directory. Outside tmux the helper creates a detached session. Names and stable IDs include the agent: r03-claude1 and r03-claude1-f015, or r03-codex1 and r03-codex1-f015. Slot numbers are separate per agent within a pass; prompts and lenses do not change identity. Mixed parallel reviewers require explicit authorization.
5. Observe through watch REVIEWER and give brief factual updates. progress.txt is the reviewer's optional stage message, not proof of progress or completion. Ctrl-C stops only the watcher. Read retained results if the reviewer fails or stalls; do not automatically retry. Completion means the reviewer signalled that it finished, not that coverage or delivery is perfect. The interactive session remains available for follow-up questions until close REVIEWER or an explicitly requested next pass. No live model checks are authorized merely to test the helper.

A preset contains only reviewer/review.md and defines what to review and how. [default](presets/default/reviewer/review.md) is an independent comprehensive review. [lenses](presets/lenses/reviewer/review.md) uses three independent subagents for regressions, repository style and rules, and comprehensive review. Explain that delegation when proposing lenses and honor the user's delegation rules. Subagents write their own drafts; the main reviewer checks evidence, reconciles duplicates and publishes the results. Select a preset through the INI settings or prepare --preset. The skill always supplies [reviewer policy](prompts/reviewer/policy.md) for repository instruction discovery, restrictions, shared subagent instructions and evidence checking, and the [publication protocol and severity grades](prompts/reviewer/protocol.md) for artifacts, ownership, merged names, draft accounting and completion after all subagents return or stop. It adds [follow-up instructions](prompts/reviewer/followup.md) when prior context exists, then appends the reviewer ID, identity-file path, task and snapshot details. These common rules apply to both agents and every preset, including custom delegation. Author discussion and fixing prompts are read separately by the author; they are not included in the reviewer assignment. Older custom presets still supply reviewer/review.md; their other files are ignored. Prepared reviews keep their frozen prompts. These are ordinary message instructions; the selected CLI's own system prompt remains. Runtime tool exclusions and Docker mounts are enforced separately. Presets cannot replace the skill's operational instructions.

Discussion and fixing:
1. Load the skill's common author instructions with instructions discuss before discussing results and instructions fix before implementing fixes. These read [discussion](prompts/author/discuss.md) and [fixing](prompts/author/fix.md) independently of the selected preset. Explicit human instructions can change presentation and workflow; presets cannot. Sort findings by priority and always show words: P0 crit, P1 high, P2 med, P3 low, P4 info, PZ undef. Preserve stable IDs when a filename includes priority and a draft-name suffix. Do not require the human to configure files.
2. Read the report, published findings and retained drafts. An unpublished or malformed artifact is for the author to inspect, not a reason to guess its meaning or omit it. Use send for reviewer follow-up, or import-finding with the raw source artifact when needed. Retain original evidence and comply with the user's recovery rules.
3. Show counts and propose the default sequence: critical/high findings individually, approved fixes in suitable batches, an explicitly requested recheck, then all medium findings in a table with author recommendations. Discuss medium findings needing attention or selected by the human. Show low findings as a table and usually propose only two or three worthwhile fixes. Offer to inspect any or all findings in detail.
4. Use reviewer severity as the starting point. Check critical claims more carefully against author assumptions; deepen other checks only as needed by uncertainty and scope. Do not perform a second complete review of every finding. Discuss deliberate unsupported cases with the human. Preserve reviewer claims and severity separately from author assessments.
5. Record assessments and explicit decisions. Group decisions apply only to named IDs and the explicitly displayed remainder. Shorthand always refers to existing finding IDs, never table row numbers. The human can revise any decision, including during a fix batch. New decisions preserve history and do not undo completed source changes.
6. Use batch-open for the selected approved IDs; batch size is a prompt guideline, not a numeric gate. Implement in the author session by default. Delegation is optional, requires explicit authorization and remains subject to repository rules. Use batch-done --finding ID ... for the fixes actually completed and record real checks. The helper keeps before/after snapshots and the diff. Use batch-cancel for an interrupted batch; it does not revert code. Human decisions, recorded fixes and reviewer confirmations stay separate.
7. After each batch, explain the result and recommend the next step. Several batches may precede one new review. Usually finish the selected critical fixes, request a review to check them and new critical findings, then propose lower priorities after explicit verification. Never launch a review automatically. Scope full rechecks the whole branch change; scope changes checks all changes since the last completed review and necessary surrounding context. The first review requires full. Missing rechecks do not resolve findings. The human can stop or change direction at any time.

Docker is the default on Linux and macOS. Source and other reviewers' records are read-only; only this reviewer's output, temporary home and the single credentials file are writable. User settings, hooks, API-key fallback and automatic MCP loading are excluded. Claude runs interactively with bypassPermissions; AskUserQuestion, EnterPlanMode and ExitPlanMode are disabled. The default preset requests independent work; lenses explicitly delegates within one review under the same common policy. Internet access is a prompt policy unless the runtime also enforces a network restriction. Native Claude mode (runtime = native) also creates a fresh temporary HOME and CLAUDE_CONFIG_DIR; it never reuses user settings, aliases, hooks or MCP configuration. It enables Claude's built-in Bash sandbox when prerequisites are available and restricts file-tool reads to the worktree and helper/Git directories. Bash and ordinary research tools remain available without a command allowlist. The helper reports missing sandbox dependencies. Claude is configured to allow fallback when sandbox initialization fails, but commands may still fail under host restrictions; native operation has not passed release validation. This is best-effort protection, not whole-process or read-only isolation. Explain that native commands may modify source or other accessible files; use Docker for the stronger boundary. Never claim that a prepared sandbox setting proves enforcement. Native macOS selects only the default Keychain credential store independently of its clean profile. Native Claude accesses Keychain directly. Native Codex and either Docker agent use a host-side bridge: credentials are copied to a temporary file (0600) under the private user directory ~/.local/share/sst-agent-review/credentials (0700), outside source and Git mounts. Each container receives only its own file. A shared lock per Keychain item serializes bridge updates across journals and worktrees. Refreshed tokens are synchronized to the original Keychain item, and the temporary file is removed after successful session closure. Detected conflicting logins are not overwritten; synchronization failures retain the private file and report its path for recovery. No token is passed in argv or prompts. This bridge does not install a Keychain RPC service. Subscription authentication and a TTY do not prove billing treatment.

Codex also uses a fresh temporary HOME and CODEX_HOME. It starts in that isolated directory, with a private project-root marker, so reviewed-project configuration is not autoloaded. The prompt supplies the source path and asks the reviewer to read repository instructions as criteria. Hooks, plugins, apps, memory import, host skill discovery, daemon startup and automatic updates are disabled. Native Codex requests workspace-write for its temporary working directory and this reviewer's output; the source path is outside those writable roots. Approvals are disabled and sandbox failures have no unsandboxed retry. Docker supplies the filesystem boundary and Codex skips its inner sandbox there. Three subagent slots are enabled for lenses. Login status confirms the ChatGPT authentication method, not current subscription entitlement. The helper never falls back to an API key. Prepared settings and fake-CLI tests do not prove live sandbox enforcement or provider behavior. An explicitly requested live check can use scripts/smoke.py --repo WORKTREE --agent both --runtime docker --effort medium. It starts real models, checks startup, a shell command, publication and cleanup in a separate journal under .agr/.cache/smoke-*, and retains failures without retry. It does not authorize a review and must never run automatically. Real macOS verification remains a separate host check.

Close, cancel and recovery use the recorded owned runtime. A missing pane does not prove its container is gone. Cleanup failures remain explicit; follow user recovery approvals before retrying. Never guess foreign ownership or kill a process by an old PID. Preserve findings, logs and decisions when closing. Optional PR export is prepared locally with export; external publication requires its own authorization and uses the author's tooling.
