These instructions govern the author's discussion of review results for every reviewer and preset. Use the common fixing instructions when the human chooses implementation; reviewer delegation does not authorize delegation of fixes.

Explain the current stage and recommend a next step in plain language. The human should not need documentation or configuration files. Offer alternatives at meaningful branches, with the usual choice first: "I suggest this; say yes if it fits." Honor an already explicit choice without asking again. Respect the repository's approval rules. End the turn when a decision is needed.

Start with counts by priority and retained artifacts. Use reviewer severity as the starting point. Read the actual finding and consult only the code and author context needed for an informed recommendation; do not conduct a second comprehensive review of every claim. Investigate critical findings more carefully. Deepen lower-priority checks when there is concrete uncertainty, conflicting evidence or a scope question. If the author knows a case is deliberately unsupported, explain the assumption and discuss it with the human. Declining a fix is different from proving the reviewer wrong. Do not silently hide a critical reviewer finding by lowering its priority.

Keep canonical IDs unchanged. For one reviewer use R2-F4; for mixed reviewers use R2-Claude1-F4. Always display priorities as words: P0 is crit, P1 high, P2 med, P3 low, P4 info (including nits), PZ undef. Legacy info means info and unclassified means undef. Sort findings by current priority in that order, then by numeric pass, reviewer slot and finding number; filenames start with the stable ID and do not sort by priority. Show undef explicitly and assess it from the evidence before deciding where it belongs. The priority in a filename is the reviewer's original severity, not a later author assessment. Use ASCII separators. Shorthand refers to existing finding IDs, never row numbers. Clarify ambiguous IDs. Preserve the full queue.

Make every finding understandable without opening its draft or asking what it means. For a table containing findings of one priority, show that priority once immediately above the table; omit the priority column and per-row priority suffixes. Only mixed-priority tables need a priority column. For an individual finding, show its priority immediately above the explanation. Apply these rules to follow-up answers and proposed fix batches too. Describe a concrete triggering scenario, what actually happens, what should happen, and the practical consequence for the user. Explain the proposed fix and how it prevents that consequence. For concurrency, authentication or cleanup problems, walk through the relevant events in order, naming which process, file or account each step concerns. State the conditions under which the problem occurs so the human can distinguish it from supported behavior that works. Use plain language and explain necessary technical terms. A title, ID, code location or terse table cell is not a sufficient explanation. Give enough detail for an informed decision on the first presentation; prefer clarity over brevity.

Default discussion flow:
1. Show critical and high-priority findings individually, including disagreements. Explain the claim, your judgment, the proposed action and meaningful tradeoffs. Record each human decision.
2. Suggest fixing approved critical findings in suitable batches. Several batches may precede a new review.
3. Suggest a new review after the selected critical fixes. Inspect explicit rechecks and newly reported critical findings. Missing verification is not confirmation. Ask about uncertainty or accepted limitations before proposing the move to lower priorities.
4. Show all medium-priority findings as one table with med stated above it: ID, concrete scenario and consequence, author recommendation, reason and latest recheck. Recommend fix, leave or discuss. If a finding cannot be explained clearly in a table cell, add a short explanation below before asking for a decision. Do not wait for the human to say they did not understand. Consult relevant evidence in proportion to severity and uncertainty; do not classify based only on titles.
5. Show low-priority findings as a table with low stated above it and no priority column. Usually recommend at most two or three worthwhile fixes as one batch and propose leaving the rest. This is a conversational default, not a code limit. Ask for agreement on the named set and the remainder. Do not reject anything merely because it was not selected or shown.
6. Show info findings separately as optional observations, and keep any remaining undef findings visible with their assessment limitations. Do not silently omit either group.

The human can change this flow in conversation, including asking to inspect every item. A group response can approve some existing IDs, ask for details on another, and decline the rest of the displayed group. Apply it only to that explicit group. Use assess to record priority, reason, proposal and recommendation. Use decide with one or more full IDs and the human's action and reason. fix means approved, reject means not fixing in this task, defer means explicitly postponed, pending means undecided. A recommendation alone is not a human decision.

Decisions can change at any time, including inside an open fix batch. Record a new decision and retain the old one. Adjust the intended batch and pass only actually completed IDs to batch-done. Keep human decisions, completed source edits and reviewer verifications separate. A changed decision does not undo code. If code is already changed, discuss whether any reversal is desired.

After a review, read its report, findings and remaining drafts. Resolve unpublished or malformed artifacts through their content and source evidence, with reviewer follow-up when useful. Ask the human when the intended result is unclear or recovery rules require it. Do not silently skip files, infer fixes from silence, merge findings, or treat an empty queue as proof of a complete review. Import a retained actionable artifact explicitly with its provenance when needed.
