---
name: local-review
description: Run local interactive Claude reviews in tmux, discuss critical findings individually and other findings in tables, record revisable human decisions, and fix selected findings in suitable batches.
---

Use this skill when the user requests a local review or continuation of an existing review. Do not invoke a reviewer proactively after coding or committing. State that this skill is being used at the first invocation. Follow the user's approval, Git, delegation and context-boundary rules; honor actions already explicitly authorized. A request to review does not authorize fixes, publication, additional reviewers or repeat runs.

At the beginning of a new invocation, before review work, run `python3 /path/to/this/skill/scripts/install_skill.py --check` when permitted by the current sandbox and user rules. This checks managed installations at most once per 24 hours; repository and manual copies stay unchanged. Read the SKILL.md at the concrete version path returned as `Skill`, then use its `Helper` path and adjacent files for the rest of this invocation. Do not repeat the update check after rereading, switch versions between helper commands, or move an active author workflow to a new version. Existing reviewer processes retain their original runtime and files. Updates never start reviewers.

If updating is blocked by sandbox permissions or network access, tell the user the check or update could not finish and show the manual update command: `curl -fsSL https://github.com/sintoniastrategy/agent-review/releases/latest/download/install.sh | bash`. Ask them to run it in a normal terminal outside the sandbox. Do not request broader permissions or install prerequisites automatically. The installed version remains usable; continue with its concrete path only when the user's workflow rules permit. If the updater itself cannot be executed, resolve this skill's existing path and report the restriction instead of claiming an update succeeded.

Keep the author session and its task context. Each review runs in a fresh interactive Claude session with the durable journal. The user should not need to read this skill or edit configuration: explain each meaningful stage, recommend the usual next step, and offer alternatives in conversation. Ask once at a branch when a choice is needed, then end the turn and wait. Do not ask again for an already explicit choice.

For managed installations, store personal preferences through configure and keep custom presets outside the versioned release directory. Do not edit a managed bundle to customize it; updates select a fresh bundle while preserving worktree settings.

The bundle needs Python 3.9+, Git, tmux, local Docker and a Claude subscription credentials file. It installs its own pinned Claude binary; user executables and aliases are not used. Resolve scripts/review.py relative to this SKILL.md and invoke it with --repo ABSOLUTE_WORKTREE. Read [the command reference](references/commands.md) for exact operations and file locations. The helper never commits, fetches, creates worktrees or publishes to external services.

Preparation and launch:
1. Establish task scope, worktree and explicit base using the supplied context. Git does not store a parent branch. Let the helper calculate HEAD, merge base, commit range and a snapshot including staged, unstaged and non-ignored untracked files. Detached HEAD is valid with an explicit base. Missing Git history or an ambiguous base needs human input; never invent a whole-folder review.
2. Use configure --human to show the effective agent, model, effort, preset, scope and runtime. Defaults are Claude, opus, xhigh, preset default and scope full. Explain the proposed review in plain language. Use preflight --base REF --human to check local tools, the selected base, credentials-file presence and Docker connectivity without installing or starting a model. Managed Claude checks subscription authentication before inference. Report missing prerequisites and follow recovery approvals.
3. Start a cycle with init --base REF --task-file FILE, or use sessions and status --human for an existing cycle. There is one cycle per worktree. Use note --text-file FILE for new author context. Read relevant saved decisions, not just counts.
4. Use prepare --human to freeze inputs, then start REVIEWER --human only for the requested run. Both accept the configured selection; prepare flags can override agent, model, effort, preset and scope for that reviewer. Only Claude launching is implemented. State the tmux window, attach command and artifact directory. Outside tmux the helper creates a detached session. Names and stable IDs stay r03-claude1 and r03-claude1-f015; prompts and lenses do not change identity.
5. Observe through watch REVIEWER and give brief factual updates. progress.txt is the reviewer's optional stage message, not proof of progress or completion. Ctrl-C stops only the watcher. Read retained results if the reviewer fails or stalls; do not automatically retry. Completion means the reviewer signalled that it finished, not that coverage or delivery is perfect. The interactive session remains available for follow-up questions until close REVIEWER or an explicitly requested next pass. No live model checks are authorized merely to test the helper.

The prompt files are separate by role. [Reviewer criteria](presets/default/reviewer/review.md), [reviewer policy](presets/default/reviewer/policy.md) and [follow-up instructions](presets/default/reviewer/followup.md) belong to the selected preset. The skill supplies the [publication protocol](prompts/reviewer/protocol.md), then appends the reviewer ID, identity-file path, task and snapshot details. These are ordinary message instructions; Claude's own system prompt remains. Runtime tool exclusions and Docker mounts are enforced separately. Presets never silently replace the skill's file protocol.

Discussion and fixing:
1. Load the selected author instructions with instructions discuss before discussing results and instructions fix before implementing fixes. Defaults are [discussion](presets/default/author/discuss.md) and [fixing](presets/default/author/fix.md); a preset or an explicit conversational instruction can change the presentation and workflow. Do not require the human to configure files.
2. Read the report, published findings and retained drafts. An unpublished or malformed artifact is for the author to inspect, not a reason to guess its meaning or omit it. Use send for reviewer follow-up, or import-finding with the raw source artifact when needed. Retain original evidence and comply with the user's recovery rules.
3. Show counts and propose the default sequence: critical/high findings individually, approved fixes in suitable batches, an explicitly requested recheck, then all medium findings in a table with author recommendations. Discuss medium findings needing attention or selected by the human. Show low findings as a table and usually propose only two or three worthwhile fixes. Offer to inspect any or all findings in detail.
4. Use reviewer severity as the starting point. Check critical claims more carefully against author assumptions; deepen other checks only as needed by uncertainty and scope. Do not perform a second complete review of every finding. Discuss deliberate unsupported cases with the human. Preserve reviewer claims and severity separately from author assessments.
5. Record assessments and explicit decisions. Group decisions apply only to named IDs and the explicitly displayed remainder. Shorthand always refers to existing finding IDs, never table row numbers. The human can revise any decision, including during a fix batch. New decisions preserve history and do not undo completed source changes.
6. Use batch-open for the selected approved IDs; batch size is a prompt guideline, not a numeric gate. Implement in the author session by default. Delegation is optional, requires explicit authorization and remains subject to repository rules. Use batch-done --finding ID ... for the fixes actually completed and record real checks. The helper keeps before/after snapshots and the diff. Use batch-cancel for an interrupted batch; it does not revert code. Human decisions, recorded fixes and reviewer confirmations stay separate.
7. After each batch, explain the result and recommend the next step. Several batches may precede one new review. Usually finish the selected critical fixes, request a review to check them and new critical findings, then propose lower priorities after explicit verification. Never launch a review automatically. Scope full rechecks the whole branch change; scope changes checks all changes since the last completed review and necessary surrounding context. The first review requires full. Missing rechecks do not resolve findings. The human can stop or change direction at any time.

Docker remains the default. Source and other reviewers' records are read-only; only this reviewer's output, temporary home and the single credentials file are writable. User settings, hooks, API-key fallback and automatic MCP loading are excluded. Claude runs interactively with bypassPermissions; AskUserQuestion, EnterPlanMode and ExitPlanMode are disabled. The default policy requests independent work; other policies can allow subagents. Internet access is a prompt policy unless the runtime also enforces a network restriction. Direct --no-docker mode is only for explicitly chosen already isolated environments. Subscription authentication and a TTY do not prove billing treatment.

Close, cancel and recovery use the recorded owned runtime. A missing pane does not prove its container is gone. Cleanup failures remain explicit; follow user recovery approvals before retrying. Never guess foreign ownership or kill a process by an old PID. Preserve findings, logs and decisions when closing. Optional PR export is prepared locally with export; external publication requires its own authorization and uses the author's tooling.
